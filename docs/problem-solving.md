# 문제와 해결 기록

처음 작성한 [PLAN.md](../PLAN.md)와 [SPEC.md](../SPEC.md)는 범위와 기준을 잡은 초안입니다. 이 문서는 그 뒤 작업하면서 바뀌거나 더해진 것만, 왜 바꿨는지(문제 또는 니즈), 어떻게 했는지(해결), 어떻게 됐는지(결과) 순서로 정리합니다. 결정의 원문은 SPEC 7절과 PLAN 6, 7절에 있습니다.

## 1단계, 2단계: 전투 규칙과 데이터

### 1. 게이지형 궁극기를 니케식 버스트 연계로 (2026-11-14, SPEC Q14)

- **문제**: 처음 계획한 "게이지가 차면 쓰는 궁극기"로는 레퍼런스의 핵심인 버스트 연계(I, II, III 단계를 차례로 이어 풀 버스트)가 드러나지 않았다.
- **해결**: 일반 스킬은 각자 자동으로 쓰고, 버스트는 캐릭터 고유 단계를 단계마다 하나씩 쓰게 바꿨다. 그 단계에 쓸 수 있는 아군이 후보 목록에 배치 순서로 뜨고, 숫자 키나 버튼으로 고른다. 후보가 없으면 그 단계는 쓸 수 없다.
- **결과**: 버스트 순서를 짜는 판단이 전투에 생겼다. 조작 키(Q11)도 이 구조에 맞춰 다시 정했다.

### 2. 스킬 관리 창과 스킬 세트 선택 추가 (2026-11-14 ~ 16)

- **니즈**: 스킬을 데이터 에셋으로 두는 것은 초안의 계획이었지만, 에셋 인스펙터만으로는 여러 캐릭터의 스킬을 비교하며 조합하기 어려웠다. 2단계 완료 기준인 "코드 수정 없이 데이터만 바꿔 새 스킬 추가"를 보이려면, 새 스킬을 만들어 넣고 전투에서 바로 골라 볼 길도 필요했다.
- **해결**: 스킬 관리 창을 더해 캐릭터별 스킬 세 칸을 한 화면에서 조합하고, 저장 전에 실행 중 로드와 같은 `SkillValidator` 로 검증하고, 설명 템플릿의 미리보기를 보게 했다. 캐릭터마다 두 번째 세트(B)를 두고 전투 전에 고르는 선택 화면을 붙였다.
- **결과**: B 세트 9종을 코드 수정 없이 데이터만으로 만들었고, B 세트로 자동 플레이한 한 판이 오류 없이 끝났다.

### 3. 테스트 시점 (2026-11-14, SPEC Q13)

- **니즈**: 1, 2단계 동안 규칙(데미지 공식, 버스트 구조, 자동 사격 리듬)이 여러 번 바뀌었고, 게임 기능을 먼저 정리하는 데 집중해야 했다.
- **해결**: 게임 기능이 정리된 뒤 테스트를 추가하기로 미뤘다. 그동안 Core 는 컴파일만 확인하고, 동작은 에디터 자동 플레이(로그와 화면 캡처)로 확인했다.
- **결과**: 2단계는 테스트 항목만 남기고 완료했다. 엔진과 무관한 Core 를 dotnet 으로 따로 컴파일하는 구조는 유지해, 테스트를 붙일 자리는 남겨 두었다.

### 4. 보스가 너무 빨리 쓰러짐 (2026-11-16)

- **문제**: 자동 플레이에서 보스가 18초 만에 쓰러져, 부위 파괴와 패턴 저지가 나올 시간이 짧았다.
- **해결**: 보스 체력을 10000 에서 20000 으로 올리고 팔 체력은 유지했다. 강타 예고 때 저지 표적(살아 있는 팔 먼저)을 모두 깎으면 패턴이 취소되게 했다.
- **결과**: 자동 플레이에서 보스가 버티는 시간이 33초가 되었다. 부위에 직접 피해를 넣는 확인으로 저지 성공, 팔 손상과 파괴, 파괴로 인한 그로기까지 오류 없이 이어지는 것을 봤다.

## 3단계 이후: 화면, 리소스, 빌드

### 5. PC 가로와 휴대폰 세로를 함께 (2026-11-17)

- **니즈**: 레퍼런스처럼 PC(가로)와 휴대폰(세로) 모두에서 같은 전투를 해야 했다.
- **문제**: 캔버스 배율이 높이 기준이라 세로 휴대폰(1080x2340)에서 캔버스 폭이 486 이 되어 HUD 가 화면 밖으로 넘쳤다. 카메라 가로 화각도 66도에서 19도로 줄어 양옆 적이 보이지 않았다. UI 시스템 패키지는 팝업을 열 때마다 배율 설정값을 다시 써서, 설정값을 바꾸는 방식은 쓸 수 없었다.
- **해결**: 설정값은 그대로 두고 화면 방향에 따라 기준 해상도를 돌려 계산하는 `CanvasScaler` 하위 클래스를 만들어, 짧은 변을 늘 1080 으로 맞췄다. 안전 영역 가로세로 비 1.3 을 기준으로 HUD 묶음 배치를 가로형, 세로형으로 바꾸는 부품을 두고, 세로 화면에서는 카메라가 가로 화각 34도를 지키게 했다.
- **결과**: 에디터 1080x2340 과 블루스택 가로, 세로 모드에서 확인했다. 이후 콘텐츠 빌드에서 이때 만든 레이아웃 그룹이 플레이어 빌드에서만 컴파일되지 않는 문제(기반 클래스의 `Update` 가 에디터 전용)를 발견해 고쳤다.

### 6. 보스 등장 연출 (2026-11-17)

- **니즈**: 보스가 그냥 나타나면 마지막 웨이브의 무게가 전달되지 않았다.
- **해결**: Timeline 에셋 하나로 붉은 경보 화면, WARNING 띠, 보스를 비추는 카메라 포커스를 움직이고, 그동안 게임 시간을 멈추고 HUD 를 숨겼다. 카메라는 시작 자리를 기억했다가 정확히 돌아온다.
- **문제와 수정**: 첫 캡처에서 띠가 화면 가운데의 보스를 가렸다. WARNING 을 보여 준 뒤 띠를 화면 아래로 내리도록 곡선을 고쳤다.
- **결과**: 가로, 세로 자동 플레이에서 연출 뒤 시간 배율과 조작이 원래대로 돌아오는 것을 확인했다.

### 7. 적이 뒤로 돌아섬 (2026-11-17)

- **문제**: 보스를 포함한 적이 움직이다 옆이나 등을 보였다.
- **원인 좁히기**: 동작 중 적 몸체와 모든 뼈의 회전을 재 보니 애니메이션 뼈는 12도 안쪽이었고, 보스 몸체 자체가 180도까지 돌았다. 몸을 이동 방향으로 돌리는 함수가 자리로 돌아가는 이동에서 뒤를 바라보게 하고 있었다.
- **해결**: 아군 쪽을 기준으로 이동의 좌우 성분만큼만 기울이고 최대 각도(일반 40도, 보스 25도)에서 멈추게 했다. 멀어지는 이동은 뒷걸음질로 본다.
- **결과**: 보스 부위 파괴까지 도는 자동 플레이에서 보스 7도, 돌격형 15도 안쪽.

### 8. 리소스를 Addressables 로 (2026-11-17)

- **니즈**: 프리팹, 데이터, 리소스를 실무처럼 Addressables 로 관리하고, 이전 프로젝트에서 만든 배포 패키지를 재사용하고 싶었다.
- **결정**: 원격 배포 없이 로컬 그룹만, 대신 씬 밖 리소스는 전부 실행 중에 주소로 불러오기로 했다.
- **해결**: 빌드 설정에는 Boot 씬만 두고 전투, 사격장 씬도 주소로 연다. 씬의 게임 오브젝트 묶음은 꺼진 채 저장해, 리소스를 꽂기 전에는 누구의 초기화도 돌지 않게 했다. 여러 번들이 함께 쓰는 글꼴, 셰이더, HUD 그림, 배경은 Shared 그룹으로 모았다(그룹에 넣지 않으면 쓰는 번들마다 복사된다). UI 팝업은 UI 시스템의 프리팹 공급원 인터페이스에 Addressables 구현을 꽂았다.
- **결과**: 번들 8개 16MB, 씬 번들은 133KB 로 공용 리소스가 섞이지 않았다. 중간에 사격장 탄약 표시가 "0 / 30" 으로 뜨는 문제(캐릭터를 실행 중에 만들며 초기화 순서가 바뀜)를 찾아 고쳤다.

### 9. 빌드 자동화 (2026-11-17)

- **니즈**: Addressables 빌드, Windows 클라이언트, APK 를 손으로 만들지 않고 한 번에.
- **해결**: 배포 패키지의 Jenkins 템플릿을 가져와 이 프로젝트에 맞게 줄였다. 원격 업로드와 콘텐츠 업데이트 단계는 빼고, 테스트 단계는 테스트 보류 결정에 따라 넣지 않았다.
- **문제와 수정**: 템플릿의 무결성 검사가 두 항목에서 실패했다. 에디터가 실행 중 채운 글자를 동적 폰트 에셋에 저장해 두었고, TextMesh Pro 셰이더에 D3D11 디버그 지시문이 있었다. 폰트 데이터를 비우고 지시문을 지웠다.
- **결과**: Jenkins #1 이 약 9분에 무결성 검사, 두 플랫폼 빌드, zip 과 APK 보관까지 성공했다.

### 10. 처음 실행의 빈 화면과 다시 시작의 로딩 (2026-11-17)

- **문제**: 리소스를 불러오는 동안 하늘만 보였다. 로딩 화면을 붙이자 이번에는 다시 시작할 때마다 로딩 화면이 떴다. 리소스를 씬이 소유해 씬을 다시 열 때마다 반환하고 다시 받았기 때문이다.
- **해결**: 씬마다 필요한 기초 리소스를 주소 목록으로 정의하고, 리소스는 씬을 옮겨도 남는 보관소가 쥐게 했다. 씬을 옮길 때 다음 씬도 쓰는 것과 "계속 유지" 로 표시한 것은 남기고, 나머지는 새 씬이 열린 뒤 반환한다(앞 씬이 그려지는 동안 반환하면 모델과 재질이 빈다). 다음 씬의 리소스가 이미 있으면 로딩 화면을 띄우지 않는다.
- **결과**: 처음 실행은 20개를 불러오며 로딩 화면이 뜨고, 다시 시작은 0개로 바로 넘어가며, 사격장으로 가면 16개를 반환하고 캐릭터 프리팹 3개만 남는다.

### 11. 결과 화면을 눌러도 다시 시작되지 않음 (2026-11-17)

- **문제**: "누르거나 R 키로 다시 시작" 이라고 떠 있는데 클릭에 반응하지 않았다.
- **원인**: 결과 팝업 뒤에 화면을 덮는 공유 Dim 이 깔리는데, 사격 입력은 UI 위를 누른 것을 빼도록 돼 있었다.
- **해결**: 팝업에 화면 전체를 덮는 투명한 다시 시작 칸을 두고, 끝나는 순간의 사격 클릭이 바로 이어지지 않게 0.8초 동안은 받지 않는다.
- **결과**: 클릭 이벤트가 다시 시작 칸에 닿고, 로딩 없이 0.03초 만에 새 전투가 시작되는 것을 확인했다.

### 12. 같은 글꼴이 두 벌 (2026-11-17)

- **문제**: 로딩 화면을 만들며 리소스 의존성을 보다가, TMP 기본 글꼴 설정(Resources)이 나눔고딕을 가리켜 나눔고딕이 앱 본체와 Shared 번들에 한 벌씩 들어가는 것을 발견했다.
- **해결**: 화면의 글자는 모두 글꼴을 직접 지정하고 있어, 기본 글꼴을 TextMesh Pro 기본 영문 글꼴로 돌렸다. 앱 본체에 들어가는 로딩 화면은 번들 리소스를 쓰지 않게 만들었다.
- **결과**: Windows 개발 빌드의 파일을 검사해 앱 본체에는 나눔고딕이 없고 Shared 번들에만 있는 것을 확인했다. 같은 확인 중 로컬 빌드가 빌드 도중의 설정 상태(`preloadedAssets`)를 디스크에 남겨 무결성 검사를 깨뜨리는 것도 찾아 빌드 뒤 되돌리게 했다.

### 13. 튜닝 패널의 범위 (2026-11-17)

- **문제**: 튜닝 패널은 키보드(F1)로 여는 개발 도구라 모바일 빌드에서 열 방법이 없었다.
- **결정**: 값 조정은 에디터에서 하므로 패널을 에디터 전용으로 정리했다.
- **결과**: 빌드에서는 패널과 기기 저장 코드가 빠지고, 에디터에서는 그대로 실행 중 조정과 에셋 저장을 한다.
